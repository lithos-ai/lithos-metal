# Monolith — a megakernel inference engine for Apple silicon

*Design: MPK Runtime V2, re-derived for Apple GPUs from measurements.*

Status: draft 2026-09-19; revised 2026-09-22 after the M5 Pro measurements (every change tagged **[M]** and traceable
to [the hardware report](../research/apple-gpu-probes.md) §3); **revised 2026-09-23 for the build phase**: this repo is
the standalone home of the engine (D15), the engine is model-agnostic by construction (D16, §5.13–5.14), and
speculative decoding targets a **DSpark** drafter instead of the checkpoint's MTP head (D10, §5.8,
[research note](../research/dspark.md)).
"Monolith" is a working codename (one stone = one GPU-resident program); nothing depends
on it. Companion documents: [implementation plan](../../plans/implementation-plan.md) ·
[measured hardware facts](../research/apple-gpu-probes.md) · [survey of Apple inference systems](../research/apple-inference-systems.md).

First target: [`nvidia/Qwen3.8-27B-NVFP4`](https://huggingface.co/nvidia/Qwen3.8-27B-NVFP4), batch-1 decode latency,
M3/M4/M5 families, macOS 26+ (Metal 4). The engine is model-agnostic; Qwen3.8 is its first client.

Evidence tags: **[M]** measured by us on an M3 Pro and an M5 Pro ([probes](../research/apple-gpu-probes.md)); **[S]** Apple
spec/documentation; **[R]** third-party report; **[H]** hypothesis the plan must test.

## 0. Decisions at a glance

| # | Decision | Why (one line) |
|---|---|---|
| D1 | **Keep MPK's thesis, change its mechanism.** The whole generation loop — all layers, sampling, speculative accept/rollback, stop detection — is one *GPU-resident static program* with no CPU work and no CPU↔GPU synchronization on the critical path. It is **not** one never-returning kernel. | A running dispatch is never preempted or shared on Apple9 and only unreliably on Apple10 **[M]**; macOS kills compute that starves the display after ~0.5–1.2 s and any command buffer at ~5 s **[R]**; and no in-kernel barrier we could build is meaningfully cheaper than a dispatch boundary **[M]** |
| D2 | **Static schedule, generated by a compiler** from a model graph; never hand-written per model (PR #278's kernel is 22 k hand-written lines for one model). | Generality is a requirement. The dynamic dispatcher's benefit — absorbing skew across 148 SMs × 8 ranks — has no counterpart on one symmetric GPU running a dependency chain |
| D3 | **No role specialization of SIMD-groups ("warps").** One homogeneous compute crew; no loader, mma, storer or dispatcher roles. | Roles exist on NVIDIA to drive asynchronous engines and a software-managed scratchpad. Apple has neither: threadgroup memory is no faster than device memory **[M]**, there is no copy engine, and M5's neural accelerators are invoked *cooperatively by the calling threads* **[S]** — the conclusion the Hopper port already reached for `wgmma` |
| D4 | **Crew geometry = `num_gpu_cores` threadgroups × 384 threads** (12 SIMD-groups × 32 lanes) for every kernel. | One threadgroup runs per core and 12 SIMD-groups run at full speed per core, on both chips measured **[M]** — the Apple analogue of "one 384-thread CTA per SM". Default, not law: on the M5 Pro ALU-heavy decode variants (NVFP4 at T = 1, FP8 at T = 2–4) stream 19–44 % faster with 2–9 threadgroups per core **[M]**, so *threadgroups per core* is a per-op autotuned profile value with 1 as the default |
| D5 | **One dispatch per fused op, encoded once into an indirect command buffer (ICB) and replayed.** The dispatch boundary is the barrier. Multi-op kernels with in-kernel barriers were built and measured; they are correct but never faster, so they are not used. | Dispatch boundary, including the launch of 6,912 threads: **1.6–2.7 µs**. In-kernel barrier: 2.1–2.6 µs with static slices (**3.1–3.9 µs** in the spec-compliant fenced form), 4.7–6.1 µs with stealing. With real block work every variant lands at 92–96.5 µs/op **[M]** — nothing to win, and a multi-op kernel is a long non-preemptible dispatch. M5 Pro: 1.4 vs 2.0–2.5 / 4.3–4.8 µs, and 81.5 vs 81.7–88.1 µs/op with work **[M]** — the margin widened |
| D6 | **Short dispatches *and* short command buffers.** Other GPU clients never get in during a dispatch on Apple9 and only sometimes on Apple10; between dispatches they usually get in on the M3 Pro, but the worst case — and on the M5 Pro the usual case behind a long buffer — is a wait for our whole in-flight command buffer. Command buffers carry ≤ ~16–33 ms of work while a display is attached (a tunable; more when headless). The display path itself is not such a client on the M5 Pro: `p15` (2026-09-25) kept a window at 120 Hz with 0 % late frames under 8–133 ms compute buffers, so the buffer length is a latency knob (the pump's over-run past a stop), not a frame-pacing one. | A small dispatch on a second queue waited 1.2–1.4 s behind one long dispatch; behind 800 short dispatches in one command buffer it waited 0.3–0.5 ms in 5 of 6 trials and the full 1.13 s in the other; 130–140 ms outliers behind ~155 ms buffers **[M]**. M5 Pro: behind the same 800-dispatch buffer it waited the whole 1.04–1.05 s in 3 of 4 runs, and behind a single 1.25 s dispatch it got in immediately in only 2 of 12 trials; ~15 ms buffers keep it under 1.5 ms **[M]** |
| D7 | **Self-advancing steps.** Everything that varies per step (positions, KV length, T, RNG counter, accept counts, done flag) lives in a GPU `StepState` updated by a serial op at the end of each step. The same ICB is replayed unchanged; the host only keeps the queue non-empty and drains a token ring. | Removes the CPU↔GPU sync (0.13 ms each **[M]**, plus the pipeline bubble) from sampling and from every speculative-decoding round |
| D8 | **Weights are re-laid-out at load time into a block-lane-major (BLM) pack** — the role MPK's TMA "swizzle" layouts play. A SIMD-group sweeps ~16–64 KB blocks; the order of the 32 lanes *inside* the block is a per-chip profile value: on Apple10 the lanes' k-th 16-byte words are adjacent (one load instruction covers 512 contiguous bytes), on Apple9 that order and lane-contiguous sub-ranges tie. | M3 Pro: 124–134 GB/s (81–87 % of nominal), vs 59–60 GB/s for far-apart lane stripes and 106–126 GB/s for the best conventional geometry. M5 Pro: lane-interleaved 286–295 GB/s (93–96 %) and 275 GB/s (90 %) in a real FP8 GEMV, while lane-contiguous caps at 200–219 raw and 238 in the GEMV whatever the load width, unrolling, occupancy or block size **[M]** |
| D9 | **Inside an op, SIMD-groups take static slices.** *Own-slice + steal* is available per op for uneven blocks or perturbed cores (`kernels/common/steal.metal`, the attention core's `STEAL` variant — #44). | Stealing is exactly-once and as fast as static slicing even with half the crew missing **[M]**; static slices need no atomics and rely only on Metal's dispatch semantics. On the attention core it gains 4–6 % at ≥ 8K context with T ≥ 4 (the cores' uneven progress) and loses 10–22 % below — under 1 % of a step either way, so it is off by default (decode-kernels.md §7) **[M]** |
| D10 | **Speculative decoding with a DSpark drafter**, fully on the GPU: a DFlash-style block drafter conditioned on the target's hidden states (KV injection) proposes γ tokens in one pass, a serial Markov head chains them, a confidence head scores each position, and a serial op picks the verify length from the confidence chain and the chip's measured cost-per-T table. The checkpoint's MTP head is not used in v1; drafters are plugins behind one `Drafter` contract (§5.14). | Decode reads 17.6 GB/token; the bandwidth bound is ~7–9 tok/s on an M3 Pro, ~16 on an M5 Pro. Verifying several tokens per weight pass is the only lever past it, and DSpark is the strongest public drafter for this target: Apache-2.0 drafters for Qwen3.8-27B exist (1.0–1.9 B parameters, 5 layers, block 7), report accepted lengths of 2.7–4.1 and 1.7–2.5× at batch 1 under llama.cpp **[R]**, and cost 7–21 % of a target pass per round. The measured cost of a T-token verify pass (M5 Pro: FP8 ×1.08 / ×1.11 / ×3.6, NVFP4 ×1.28 / ×1.79 / ×5.3 for T = 2 / 4 / 8 on the shader ALUs; ×1.5 for T = 8 on the accelerators **[M]**) is what the verify-length rule optimizes against |
| D11 | **Numerics contract = weight-only dequantization (W4A16 / W8A16)**, BF16 residual stream, FP32 accumulators and recurrent state, one rounding per op output. Reference = HF model on the *dequantized* weights. | Apple GPUs have no FP4/FP8 arithmetic; the checkpoint's `input_scale`s are a Blackwell throughput feature, not a semantic requirement |
| D12 | **Profiling = per-op GPU timestamps** (every op is already its own dispatch) into MPK's `.mpktrace` format and viewer; a *clock SIMD-group* is available for intra-op traces. | MSL has no in-kernel clock; a free-running atomic tick counter gives ~48 ns ticks ±1 % **[M]** |
| D13 | **Stack:** C++/Objective-C++ runtime, Python front-end and compiler, MSL kernels specialized with function constants and cached in binary archives. Standalone repo; MPK code reused under Apache-2.0 where it fits; no MPK/Mirage naming. | Decided 2026-09-19 |
| D14 | **Inter-op overlap only where it is free:** an ALU-bound op and a bus-bound op that do not depend on each other are encoded as un-barriered sibling dispatches, both at full crew geometry. No weight pre-staging across dependencies (MPK V2's form of pipelining), and no hand-partitioning of cores. | The memory bus saturates with ~half of the M3 Pro's cores, so an ALU-bound op hides completely (86–114 %, within noise) inside a bus-bound one; two bus-bound ops overlapped gain 0 %; manual core splits were sometimes *slower* than serial **[M]** (§5.12). M5 Pro: the bus saturates with 6 of 20 cores, and the ALU-bound op hides 102–126 % when it is encoded *before* the bus-bound op but only 1–29 % when encoded after it — encode order is a profile rule **[M]** |
| D15 | **Standalone repo: copy, never depend.** Files from MPK/mirage (Apache-2.0) and from MLX, llama.cpp, tinygrad, DeepSpec, DFlash (MIT) and gpt-oss (Apache-2.0) may be copied in verbatim or adapted, keeping their license headers and a `third_party/NOTICE` entry. There is no import of, submodule of, pip/CMake dependency on, or naming from mirage/MPK; this repo builds, tests and runs on its own. | The engine is a new codebase for a different execution model; a dependency on MPK would drag in CUDA-shaped abstractions and couple two release cycles. Copying keeps the proven algorithms (GDN recurrence, GQA decode, accept scan, goldens, profiler format) without the coupling |
| D16 | **Model-agnostic by construction.** Model-specific code lives only under `monolith/models/<name>/`; everything else is reached through registries (models, layers, formats, ops, drafters, chip profiles) and checked by the compiler's coverage guard. Adding a model is a package plus a golden script, never an edit elsewhere — enforced by the generality milestone and a CI diff check (§5.14). | Generality is a v1 requirement; PR #278's 22 k hand-written lines for one model is the failure mode to design against |

The two questions put to this design, answered in §7: **warp specialization — no**; **static megakernel — yes to
"static", no to "one kernel"**. On Apple silicon the megakernel is a pre-encoded, self-advancing GPU program of
fused whole-GPU dispatches.

## 1. The target, in numbers

`Qwen3_5ForConditionalGeneration` text stack: 64 layers = `[GDN, GDN, GDN, full-attention] × 16`; hidden 5120;
SiLU-gated MLP 17408; vocab 248,320; full attention 24 q / 4 kv heads × 256 with per-head q/k RMSNorm, partial RoPE
(64 of 256 dims) and a sigmoid output gate; Gated DeltaNet 16 k / 48 v heads × 128, depthwise conv (W = 4), FP32 state
`[48,128,128]` per layer; one BF16 MTP layer (unused in v1). Architecture details and the partial-RoPE / γ-folding tricks come from
MPK's bring-up (`mirage/plans/qwen38-mpk-v2-tp8.md`).

Checkpoint, read from the safetensors headers (21.92 GB):

| Group | Bytes | Format | Read per decoded token |
|---|---|---|---|
| MLP `gate/up/down` × 64 | 9.63 GB | **NVFP4**: `U8` two nibbles/byte + `F8_E4M3` scale per 16 + FP32 tensor scale | all |
| GDN `in_proj_qkv`, `in_proj_z`, `out_proj` × 48 | 5.54 GB | **FP8 E4M3**, per-tensor FP32 scale | all |
| GDN `in_proj_a/b`, conv1d, `A_log`, `dt_bias`, norm | 0.05 GB | BF16 | all |
| Attention `q/k/v/o_proj` × 16 | 1.68 GB | **FP8 E4M3**, per-tensor scale | all |
| `lm_head` | 0.72 GB | NVFP4 | all |
| `embed_tokens` | 2.54 GB | BF16 | one row |
| MTP head | 0.85 GB | BF16 (excluded from quantization) | not loaded — v1 speculates with a DSpark drafter (next row) |
| Vision tower | 0.92 GB | BF16 | not loaded (text-only v1) |
| **DSpark drafter** (separate checkpoint, e.g. `DimInfer/Qwen3.8-27B-Dspark-v1`, Apache-2.0) | 1.3 GB NVFP4 / 2.0 GB Q8 / 3.7 GB BF16 | 5 full-attention layers on hidden 5120 (GQA 32/8, head 128), a projection of 5 tapped target layers, a rank-256 Markov head, a confidence head; shares the target's `embed_tokens` and `lm_head` | once per speculative round, at T = γ = 7 |

**Weights read per token: 17.6 GB**, plus ~0.3 GB of GDN state read+write and 64 KB × context of KV (2.1 GB at 32 K).
A speculative round adds the drafter pass, `lm_head` at T = γ and γ reads of the Markov head's W₂ (127 MB in BF16):
2.6–5.3 GB depending on the drafter's format, i.e. 15–30 % of a target pass, for γ = 7 candidate tokens.
Decode is bounded by memory bandwidth:

| Chip | Nominal GB/s | Bound, tok/s (17.9 GB/token) | Fits? |
|---|---|---|---|
| M3 Pro (local) | 153.6 | 8.6 — **6.9 at the 124 GB/s we measured** | 36 GB config ✔ |
| M4 Pro / M5 Pro | 273 / 307 | 15 / 17 | ≥ 48 GB configs ✔ (the 24 GB M5 Pro measured here does not: 19 GB working-set limit **[M]**) |
| M3 Max / M4 Max / M5 Max | 410 / 546 / 614 | 23 / 31 / 34 | ✔ |
| M3 Ultra / M5 Ultra | 819 / 1229 | 46 / 69 | ✔ |

Everything in this design serves two goals: get as close to that bound as the hardware allows, then get past it by
producing more than one token per weight pass.

## 2. What transfers from MPK, and what does not

MPK wins on NVIDIA by (i) removing kernel-launch cost and CPU↔GPU synchronization, (ii) scheduling hundreds of tasks
per op across 130–150 SMs while loader warps stream weights into a software-managed SMEM asynchronously, and
(iii) doing collectives in-kernel. We measured what each is worth on Apple silicon instead of assuming it.

| MPK benefit | On Apple silicon | Evidence |
|---|---|---|
| Launch overhead eliminated | **Already small for a large model.** Metal encodes a dispatch in 0.13 µs of CPU and executes its boundary in ~1.3–2.7 µs of GPU time (others report 2.6–5 µs on other chips **[R]**). A 1,240-dispatch token costs ~2 ms: 1–2 % of a 27B token on an M3 Pro (M5 Pro: 1.3–1.6 µs per dispatch and a ~62 ms token, so 330 dispatches are 0.8 % **[M]**), ~7 % at 30 ms/token — but 40–70 % of the token for 0.6–3 B models and 3B-active MoE, where today's engines sit at 22–57 % of the bandwidth bound **[R]**. What *is* expensive in existing engines is framework structure: MLX splits a decode step into 45–90 command buffers at ~20 µs each **[R]**. | P7, P10 **[M]**; [survey](../research/apple-inference-systems.md) §1, §5 |
| CPU↔GPU sync eliminated | **Real.** 0.13 ms per sync plus the bubble; decisive where an engine must sync every step: CPU-side sampling and, above all, every speculative-decoding round. | P7 **[M]** |
| Async data movement overlapped with compute | **Does not exist.** No copy engine, no fast scratchpad; the memory hierarchy is hardware-managed. | P8 **[M]**; Apple9+ "dynamic caching" **[S]** |
| Fine-grained dynamic task scheduling | **Moot.** Decode is a chain of ops that each want the whole memory bus; one device, no network skew. Intra-op balance is handled by stealing where needed. | §5.3 |
| One long-lived kernel | **Counter-productive.** Not preemptible, watchdog-limited, and its in-kernel barriers cost more than dispatch boundaries. | P6, P6b, P10 **[M]** |
| In-kernel collectives | Out of scope (single device). Thunderbolt-5 RDMA is CPU-driven send/recv **[S]**. | — |

Where the wins actually are on Apple — the ledger this design is built on:

1. **Streaming efficiency.** On dense 7B 4-bit decode llama.cpp reaches 57–80 % of nominal bandwidth depending on the
   chip (62 % M3 Max, 70 % M4 Pro, 80 % M5 Pro), and MLX's 4-bit GEMV kernel alone streams at 87 % on an M5 Pro; the
   practical ceiling is ~85–90 % **[R]**. The crew geometry sweeping block-lane-major packs reached 81–87 % on the M3 Pro
   in a raw-read microbenchmark, +5 % to +17 % over the best conventional geometry depending on the run **[M]**. On the
   M5 Pro a first real FP8 GEMV at the crew geometry reached 90 % (275 GB/s) — at *parity* with the conventional
   many-small-threadgroups geometry, with the lane order inside the block worth +16 % and the same kernel for NVFP4
   ALU-bound at 59 % **[M]** (`p13`). So the lever is *data layout and decode cost*, not geometry, and it is not a
   megakernel property. Honest sizing: for a dense-ish 27B model it is worth a few percent to ~15 % over today's
   engines, and for NVFP4 it is a kernel-study problem before it is a win (plan M1).
2. **Tokens per weight pass.** DSpark speculative decoding with the draft, the Markov chain, the verify-length
   choice and accept/rollback all on the GPU: no sync per round, no host re-encode, recurrent-state rollback handled
   on the GPU. Public drafters for this exact target report 1.7–2.5× at batch 1 under llama.cpp on a discrete GPU
   **[R]**; here the round is cheaper (no host in the loop) and the verify pass dearer (NVFP4 on shader ALUs), so
   expect 1.5–2.5× **[H]**, chosen per chip by the verify-length rule.
3. **Whole-step static fusion.** ~1,240 framework-level ops → ~330 fused whole-GPU dispatches (norm folded into the
   GEMV input, gate+up+SiLU in one pass, the whole GDN mixer per head, residual adds as epilogues): fewer
   materializations, fewer barriers, fewer loads per weight.
4. **Zero CPU in the loop.** ICB replay costs 0.01 ms of host time per token **[M]**; sampling, acceptance and stop
   detection run on the GPU; the host never decides what runs next.

> A candid summary: what carries over from MPK is the *thesis* (compile the whole generation loop into a GPU-resident
> static program) and much of the *discipline* (layout for the streamer, fused task bodies, monotone state, staged
> numerical gates). What does not carry over is the *mechanism* — one persistent kernel with specialized roles —
> because every hardware reason for it is absent here, and the one thing it would save (launch overhead) is already
> ~1 % and is removed more cheaply by replaying a pre-encoded command stream.

| `%globaltimer` | none ⇒ per-dispatch GPU timestamps; clock SIMD-group for intra-op traces **[M]** | |

### 5.1 The step program

A **step** is one forward pass over `T` tokens (T = 1 plain decode; T = 1 + L when verifying L draft tokens; T ≤ T_max when
chunking a prompt) plus sampling and state advance. The compiler emits a **step program**: an ordered list of fused
ops, each one Metal dispatch with the crew geometry; ~330 for Qwen3.8 (5 per layer).

**Why ~330, and not 1 or 1,240.** A dispatch boundary is needed exactly where a consumer block reads data produced by
*other* blocks of the previous op — an all-to-all dependency — because every SIMD-group must finish the producer
before any may start the consumer. A GEMV is all-to-all on its input (each output row reads the whole input vector);
the token mixer is all-to-all on the projection feeding it (one head's q/k/v/z rows were computed by different row
blocks). Everything else is block-aligned and is fused into a neighbour. That leaves five stages per layer, for both
layer types:

| # | Dispatch | All-to-all on | Fused into it (block-aligned, no barrier) |
|---|---|---|---|
| 1 | stacked input projection (`in_proj_qkv|z|a|b`, or `q|k|v` + gate) | residual stream `h` | input RMSNorm scaling (its statistic comes from the previous op's epilogue) |
| 2 | token mixer (`gdn_mixer` per v-head, or `gqa_decode` per (q-head, KV-chunk)) | the projection outputs | conv + SiLU, L2-norm, gates, recurrence, gated norm — or q/k norm, RoPE, KV append, output gate |
| 3 | output projection | the mixer output | residual add; per-block partial Σh² for the next norm |
| 4 | `gate|up` projection | `h` | post-attention RMSNorm scaling; SiLU·mul |
| 5 | `down` projection | the MLP activation | residual add; per-block partial Σh² for the next layer |

64 × 5 = 320, plus embed, `lm_head`, the sampling combine and the per-step advance ≈ 325–330. A DSpark round adds
~50: 5 draft layers × 5 stages, the feature projection for the newly accepted positions, `lm_head` at T = γ, γ
Markov-bias + argmax pairs, the confidence/verify-length select and the accept scan. This is the **dependency depth of the model** in all-to-all stages, not an engine choice: it cannot go lower
without changing the math (RMSNorm between stages 3 and 4 is nonlinear, so they do not fold), and a barrier has to
exist at each of these points in *any* implementation — the only question is what implements it, and the dispatch
boundary is the cheapest we measured (§5.3). The count goes *up* if a fusion is not done: separate norm-statistic
reductions +128, a separate q/k-norm + RoPE + KV-append +16, unstacked mixed-format projections (FP8 `qkv|z` vs BF16
`a|b`) +48 — ≈ 520 worst case. One split is deliberate: §5.12 emits each mixer's gate projection as an un-barriered
sibling of the mixer core (+64 dispatches, no extra barrier) because that pair can overlap. At ~1.8 µs each, 330 vs 520 is ~0.3 ms per token, so those fusions are justified by
memory traffic and materializations, not by dispatch count. *The count is derived by hand from the graph; no compiler
exists yet to confirm it.*

* The program is encoded **once** into a compute ICB: pipeline, buffer bindings with offsets, threadgroup sizes, and
  a barrier wherever the compiler found a dependency (ICB dispatches are concurrent unless barriered **[S]**). A step
  is then one `executeCommandsInBuffer` — 0.01 ms of host time **[M]**. Metal 4 command buffers are re-encodable but
  not replayable **[S]**, so the ICB is the replay mechanism under both Metal 3 and Metal 4 encoders. ICBs have no
  `setBytes`, and their buffer-bind offsets are 32-bit **[R]**: every op reads a small parameter record from a buffer,
  and large weight buffers are addressed through 64-bit GPU addresses stored in that record (tier-2 argument buffers +
  one residency set) rather than through bind offsets. A session's programs (the dynamic-T program; a static one per
  T the bench or a test asks for) share buffers **by name** — weights, states, StepState, the ring, activations — and
  a parameter record is the one thing never shared: its name carries the program kind and `Engine` allocates its own
  (two programs' counters once met on one name, and three tiles ran another GEMV's record, #113).
* Prior art: tinygrad replays a per-step ICB; OpenAI's gpt-oss Metal reference encodes N decode iterations with GPU
  sampling and on-GPU token feedback into one command buffer; uzu and Apple's Core AI sample engine keep 1–3 steps in
  flight **[R]**. None compiles a general model into a replayed, self-advancing program; that is the gap this engine
  fills. If a driver bug makes ICB replay unusable, the same program is re-encoded per step (0.16 ms/token **[M]**,
  still no synchronization).
* Nothing in the encoded program changes between steps. Whatever varies is read from `StepState` (§5.4). Ops whose
  work grows (attention over a longer KV) keep the fixed crew geometry and loop over a dynamic number of blocks
  in-kernel, so no indirect dispatch or re-encode is needed.
* Each dispatch is short (≈ 0.4 ms on an M3 Pro for this model) and each command buffer replays a *range* of the ICB
  worth ≤ ~16–33 ms of work while a display is attached (`executeCommandsInBuffer:withRange:`; a profile tunable,
  larger when headless). Other GPU clients are normally served between our dispatches, but the measured worst case is
  a wait for one whole command buffer **[M]** — so its length, not the step's, bounds the stall we can cause. On the
  M3 Pro that is ~5–9 command buffers per step at a few tens of µs each; on fast chips or small models several steps
  fit in one.

### 5.2 Crew kernels

Every op is a **block body**: a pure function of `(block_id, lane, op_args, step_state)` that reads its inputs and
writes a disjoint part of its outputs. All kernels are dispatched as `num_cores × 384`, and each SIMD-group executes
its blocks.

* *Lockstep rule.* The 32 lanes of a SIMD-group share control flow, so a block is always executed by a whole
  SIMD-group and its trip counts are lane-uniform.
* *Block shape* is chosen per op by the compiler from the chip profile: GEMV/GEMM — R rows of the weight matrix
  (R = 8–32, ~32–64 KB of packed weights); attention — one (q-head, KV-chunk); GDN mixer — one v-head;
  elementwise — a fixed span; vocab argmax — a row range.
* *Op classes.* `MAP` (disjoint outputs per block); `REDUCE` (per-block partials, combined in block order by a small
  follow-up dispatch — deterministic); `SERIAL` (a one-SIMD-group dispatch: sampling finalize, accept/reject, state
  advance).
* *Slices.* SIMD-group `s` owns blocks `s, s+S, s+2S, …` (or a contiguous range when locality matters). No atomics;
  correctness rests only on Metal's guarantee that a dispatch completes before a barriered successor starts.

### 5.3 In-kernel synchronization: what we built, measured, and do not put on the hot path

The NVIDIA design lives on in-kernel synchronization, so we implemented it faithfully and measured it
(`probes/p10_claim_protocol`): 320 ops × 544 blocks in **one** dispatch, a barrier after every op.

* **It works.** *Own slice + steal*: each nominal SIMD-group owns a contiguous slice behind its own cursor, drains
  it by bounded `compare_exchange`, then steals from other slices in a per-SIMD-group permuted order; lane 0
  broadcasts each claim with `simd_broadcast_first`; a monotone `done` counter is the barrier. Exactly-once execution
  and zero timeouts in every configuration — including half the crew missing and 2×/4× surplus threadgroups — so
  co-residency of all threadgroups, a hard correctness requirement in NVIDIA MPK, is only a performance property
  here. A spec-compliant build (`coherent(device)` buffers, `atomic_thread_fence(mem_device, seq_cst,
  thread_scope_device)` at every publish and barrier exit, MSL 3.2) costs +0.6 to +1.7 µs per op. A single global claim
  cursor is *not* viable (CAS contention: +27 %).
* **It does not pay.** Per barrier: 2.1–2.6 µs with static slices (3.1–3.9 µs fenced, which is what the spec
  requires), 4.7–6.1 µs with stealing — against **1.6–2.7 µs for a dispatch boundary**, which also launches the 6,912
  threads. With 30 µs blocks every variant lands at 92–96.5 µs/op. A multi-op kernel is also one long non-preemptible
  dispatch (§0 D6) and is opaque to Apple's tools.

So the hot path uses dispatch boundaries. The protocol stays in the toolbox for two uses: **intra-op stealing** in
ops whose blocks are uneven (long-context attention, MoE experts) or when cores are perturbed, and re-evaluation on
chips where the trade-off might differ (plan M7, time-boxed).

### 5.4 GPU-autonomous control

`StepState` (one small buffer): `step`, per-sequence `position`, `kv_len`, `T_this_step` (= 1 + L), `pending_tokens[T_max]`,
RNG counter, speculative bookkeeping (`anchor`, `draft_tokens[γ]`, `confidence[γ]`, `verify_len L`, `accepted`, GDN
checkpoint index, drafter context length), `done`, `error`, token-ring head.

* The last dispatch of a step is `SERIAL`: finalize sampling, run accept/reject, choose the GDN checkpoint to keep, set
  the next round's anchor, append to the **token ring** (shared memory — the CPU reads it without a copy; each 8-byte
  slot carries the token and its sequence number in one store, because the host drains while later command buffers
  are still running and cannot trust a head counter it reads from an in-flight buffer), check stop conditions (EOS set,
  max length, stop-token table), advance positions and `step`. It also guards the caches: a `Program` carries its
  `context_capacity` (the smallest KV cache of the target and, with a drafter, of its context less the block it
  appends after it), the verify-length select clamps L to the target's rows, and a step whose first position would
  reach the capacity sets `error = 2` and `done` — no kernel ever indexes past a cache (`error = 1` is the token ring
  overflowing). The host refuses a request that cannot fit before it starts; the guard catches the pump's over-run.
* **Host pump.** The host keeps a few command buffers in flight (≈ 50–100 ms of queued work), each replaying one
  bounded range of the step ICB (§5.1). A completion handler drains the token ring and enqueues more. When `done` is set, steps already queued return at their first
  instruction (~2 µs per dispatch). The host never waits on the GPU to decide what runs next, so host latency is off
  the critical path.
* **Prompt processing** in v1 reuses the decode program with T = T_max per step (decode-shaped kernels, as MPK's dense
  lane and the Hopper port do). A dedicated prefill path (tiled GEMM / MPP TensorOps, FlashAttention-style SDPA,
  chunked GDN scan) is post-v1 — prefill is explicitly not a v1 gate.

### 5.5 Memory and weight layout

* **Weights** are converted once into `weights.pack`, page-aligned and mmap'ed straight into a few large `MTLBuffer`s
  (`newBufferWithBytesNoCopy`; each below `maxBufferLength`, 21 GiB on the M3 Pro), one residency set.
* **Block-lane-major (BLM) pack.** For a matrix `[N, K]` with R-row blocks: block `b` holds rows `[bR, bR+R)`; lane ℓ
  owns the column stripe `[ℓK/32, (ℓ+1)K/32)` of every row in the block. The order *inside* the block is a profile
  value. *Lane-contiguous* (M3 Pro, 124–134 GB/s): lane ℓ's stripe of all R rows, then its scales — one contiguous
  ~1–2 KB range per lane. *Lane-interleaved* (M5 Pro: 286–295 GB/s raw and 275 GB/s in a real FP8 GEMV, where
  lane-contiguous caps at 65–71 %): the 32 lanes' k-th 16-byte words are adjacent, so every load instruction reads
  512 contiguous bytes. Either way the SIMD-group sweeps one contiguous ~16–64 KB block; on the M3 Pro the two orders
  tie **[M]**. Fusions are layout decisions too: gate and up
  rows are interleaved so one pass yields `silu(g)·u`; `q|k|v` and `in_proj_qkv|a|b` are row-stacked into single ops.
  The mixer's gate projection (`in_proj_z`; the gate half of `q_proj`) is stacked with them or packed as its own op,
  depending on whether §5.12's sibling overlap is enabled for the chip. R, stripe order and scale placement are
  autotuned per chip. A GEMV's work item is a block or a *share of a block's rows* (`RSPLIT`, autotuned): a
  1024-row slab is 64 blocks — a quarter of the M5 Pro's 240 SIMD-groups — and 512 items of two rows fill the crew
  (o_proj and down 2.1–2.2× faster at T = 1 on the 0.6B; the 8B's 4096-row slabs are 256 blocks, 1.07 waves, and
  split too); the arithmetic per row is the same, so the outputs are bit-identical (decode-kernels.md §10).
* **Formats** are plugins: `unpack(checkpoint tensors) → pack` plus an MSL `decode` snippet used by the GEMV
  template. v1: NVFP4 (E2M1 LUT × E4M3 block scale × FP32 tensor scale), FP8-E4M3 per-tensor (256-entry LUT), BF16;
  built since: INT8 groups and **affine INT4 groups** (`int4_affine`, the MLX / AWQ / GPTQ family, `w = scale·code +
  bias`, mlx 0.32's quantizer reproduced bit-exactly): the decode contract grew a per-group bias hook (`decode_bias`,
  the GEMV adds `bias · Σx` per group), a quantized table can be gathered as the embedding (`EMBED_DEQUANT`), and a
  lane stripe may be *ragged* — not whole words, starting inside a scale group (K = 3584): the unit is
  `[payload | scales | pad]` with the scale bytes in the partial tail word, and the kernels index a stripe's groups
  from its offset (`LANE_OFF`, `GROUP_SEG`). The unit's padding to 16 bytes is bus bytes (NVFP4 at K = 4096: 64 + 8
  → 80, 11 %), so a pack can keep the block's scales in their own region after its payload words instead
  (`scale_placement: block`, #101): the unit is whole payload words, a lane's scales start `(lane·S) % 16` bytes
  into a word of the region and the kernels load `scale_words` words from there (`SCALE_WORD`, `SCALE_SOFF`); the
  packer keeps the inline form where it is already tight (INT4's 64 + 16, a ragged tail half-word). With the region
  a 4- or 8-byte payload (K = 256 or 512 for NVFP4) is not padded to a word either: 4 or 2 lanes share one
  (`LANES_PER_WORD`, the shader GEMV's `sub_word` select) and a stripe narrower than a scale group carries the group's
  scale once per lane — the DSpark Markov head's 151936 × 256 in NVFP4 is 24 MB instead of 78. The placement is a
  profile value. Manifest version 2 also records `scale_lane_divisor`: affine INT4 groups shared by adjacent
  narrow stripes are stored once in the block region (K = 1024: 64 scale bytes per row instead of 128).
  Payload order and dequantization stay unchanged; the reader accepts version 1 with a divisor of 1.
  `PackLayout.share_scales=False` / `pack_weights.py --no-share-scales` retains the original layout for comparisons.
  Manifest version 3 additionally supports `scale_order: payload` for aligned, interleaved NVFP4 block scales:
  `[row][word][lane][two scale bytes]`. The weight codes, scale bytes, row scales and block sizes do not change;
  adjacent physical weight groups read adjacent scales. Matrix/row kernels read pairs directly, while legacy
  GEMV and embedding kernels reconstruct a lane's scale words. `pack_weights.py --scale-placement block
  --scale-order payload` opts in; ineligible slabs retain their existing order. Versions 1 and 2 remain readable,
  and a payload-order marker in an older manifest is rejected. Autotuning distinguishes the scale layouts.
  Next: MXFP4, GGUF K-quants.
* **State.** KV cache per attention layer (BF16 in v1; FP8/INT8 later — at long context KV traffic overtakes the
  weights); GDN recurrent state FP32 `[48,128,128]` + conv state, each with `γ+1` checkpoint slots for speculative
  rollback; the drafter's injected-context KV (5 layers × 8 KV heads × 128 × K and V ≈ 20 KB per committed token,
  append-only: features of rejected positions are never appended, so it needs no rollback) and a feature-tap buffer
  for the T positions of the verify pass; activation arena planned by liveness (a few MB); `StepState` (its
  host-written `stop_at` is the ring head at which the closing serial op sets `done`, so the host can queue full
  command buffers for a request of any length and the steps behind the request return at once — no over-run work,
  as after an EOS); optional trace buffer.

### 5.7 Compiler

* **IR.** Typed tensor graph; shapes symbolic in `T` and context length; ops carry reads/writes, block domain, class
  and a cost model. Layers of the same type share one op template plus a per-layer weight-slab table (PR #278's
  layer-type templating), so the kernel set is independent of depth: ~12 pipelines serve all 64 layers.
* **Passes.** canonicalize → fuse (vertical chains, norm folding, epilogues, row-stacking) → select weight packs →
  partition into block domains → place barriers (only on real dependencies; independent ops may run concurrently
  inside the ICB) → plan memory → emit.
* **Emit.** Hand-written, tested *block bodies* + generated kernel wrappers specialized by function constants;
  `program.json`; pack manifest. Pipelines are compiled at install/first run and cached in an `MTLBinaryArchive`.
  Math mode is `safe` for softmax/norm/sampling bodies (MSL fast-math is on by default **[S]**) and may be relaxed in
  GEMV inner loops if the layer gates hold.
* **Chip profiles.** `{cores, full-speed SIMD-groups per core, GB/s, lane order, threadgroups per core, block sizes,
  R, T_max, γ, cost(T) per format, sibling-order rule, max_cb_ms}` — produced by the probe suite and an autotuner at
  install time, never hard-coded. The autotuner is `tools/profile_writer.py` (#49): the kernel harnesses measure the
  lane order, the threadgroups per core, `cost_T` per format at the best geometry per T, the tile's rows and the
  accelerator switch, and the attention kernel; the probes' values (sibling order, `max_cb_ms`) carry over from the
  hand-derived record. Decisions follow the autotuner's noise rule (3 %; a tie keeps the file's value).
* **Dynamic T.** With DSpark the verify length changes every round, so `T_this_step` is read from `StepState` by every
  kernel (T_max = 1 + γ fixed at compile time; the crew geometry never changes). Where the best kernel differs by T —
  the shader GEMV at T = 1, the tensor-ops tile above it on Apple10 (the profile's `accelerator_min_t`, 2 on the
  M5 Pro for every format; #51) — both variants are encoded and the one
  not selected returns at its first instruction (a predicated dispatch costs ~1.4 µs **[M]**; 2.7 in the 8B's step);
  `executeCommandsInBuffer:indirectBuffer:`, which lets the GPU choose the ICB range, is the optimization if those
  µs ever matter. Variants a program can never take are not encoded: under the cost-aware or a fixed L ≥ 1 rule a
  decode step runs at T = 1 + L ≥ 2, so the step's T = 1 variants are pruned and the next variant's range starts
  at 0 (a prefill chunk of one token runs on it); the injection's variants (`n_inject` can be 1), an LM drafter's
  chain rows (`n_chain`, one variant; its first step's `n_inject + n_chain` rows, bound to T_max + 1) and the threshold
  rule's (L = 0 is possible) stay. A tile's input is read in `x_permute`'s order; when the input is un-normed and
  the GEMV runs on the tile alone, its producer writes that order itself (`PERM_OUT`: the attention merge for
  `o_proj`, the gate|up tile's silu·mul epilogue for `down`) into the tile's scratch and the permute dispatch is not
  emitted — the normed inputs keep theirs, which applies the norm on the way.

### 5.8 Speculative decoding with a DSpark drafter

DSpark ([DeepSeek, July 2026](../research/dspark.md)) is a confidence-scheduled, semi-autoregressive drafter: a
DFlash-style *block drafter* — a small transformer that reads the target's context through **KV injection** and
proposes a whole block of γ tokens in one forward pass — plus a *serial Markov head* that restores intra-block token
dependency at the cost of a rank-256 bias per position, plus a *confidence head* that predicts each position's
acceptance probability so the verifier can choose how many draft tokens to verify. Drafters for Qwen3.8-27B are public
(§1); the target's MTP head is not used.

**The round, as step-program ops** (all on the GPU; the host sees only tokens):

1. *Feature append.* The previous verify pass tapped the residual stream after target layers {l₁…l₅} for its T positions
   (a free epilogue of stage 5). For the positions the accept scan committed: `Wc · [h_l1; …; h_l5]` → each draft
   layer's k/v projections → appended to the drafter's injected-context KV (append-only, no rollback).
2. *Draft pass* at T = γ: input = anchor token (the last committed token) + γ−1 mask embeddings; 5 draft layers
   (attention over injected context + block, MLP) → `h₁…hᵧ`; `lm_head` at T = γ → base logits `U₁…Uᵧ`. These are
   the target's own layer bodies at T = γ with the drafter's weights — no new GEMV or attention code.
3. *Markov chain*, γ sequential steps: `x₀ = anchor`; for k = 1…γ: `logits'ₖ = Uₖ + W₂ᵀ W₁[xₖ₋₁]`, `xₖ = argmax`
   (greedy) or a Gumbel draw; `cₖ = σ(wᵀ[hₖ; W₁[xₖ₋₁]])`. Each step is a bias GEMV over the vocabulary (W₂: 256 × V,
   127 MB in BF16) followed by an argmax — 2 dispatches and ~0.45 ms on an M5 Pro per position, 3 ms per round for
   γ = 7. Pruning the bias to the top-M base logits is an **[H]** optimization that is exact only under a bound on
   |bias|; v1 computes the full bias.
4. *Verify-length select* (`SERIAL`): with survival probabilities `aₗ = ∏ᵢ≤ₗ cᵢ` (after per-position temperature
   calibration, STS, shipped with the drafter or fitted once), choose
   `L = argmax_{0≤l≤γ} (1 + Σᵢ≤ₗ aᵢ) / cost(1 + l)`, where `cost(T)` is the profile's measured cost of a T-token target
   pass in units of a T = 1 pass (M5 Pro shader ALUs: FP8 1 / 1.08 / – / 1.11 / … / 3.6, NVFP4 1 / 1.28 / – / 1.79 /
   … / 5.3 for T = 1 / 2 / 3 / 4 / … / 8; the tensor-ops tile 1.03 / 1.09 (NVFP4 / FP8) for any T ≤ 16 **[M]**, so
   with the accelerator on the table is the shader's row at T = 1 and the tile's above — #51). This is DSpark's hardware-aware
   scheduler reduced to batch 1: the confidence chain supplies the expected acceptance, the chip profile the cost.
   Write `T_this_step = 1 + L`.
5. *Target verify pass* at T = 1 + L (the ordinary step program with dynamic T), tapping features for the next round.
6. *Accept scan* (`SERIAL`): greedy match, or rejection sampling with `min(1, pₜ(xₖ)/p_d(xₖ))` — with greedy
   drafts (a point-mass `p_d`) this is exactly "sample `yₖ ~ pₜ` at every position with the ordinary sampler and
   accept `xₖ` iff `yₖ = xₖ`", so the scan compares the sampled tokens with the drafts and needs no mode of its own;
   commit the accepted prefix plus the target's bonus/corrected token; commit the recurrent states of the accepted
   prefix, advance the KV by `accepted + 1`, set the next anchor, append tokens to the ring, check stop conditions.

**Cost model.** Per round: drafter weights once (1.3–3.7 GB), `lm_head` at T = γ (0.72 GB), γ × W₂ (0.9 GB in BF16,
0.45 in INT8), plus the verify pass at `cost(1 + L)`. The shader-FMA `cost(T)` table (×1.8 at T = 4 for NVFP4) was
the reason the round could not pay for itself on the M5 Pro; the tensor-ops tile (§5.6, #50/#51) makes every T ≤ 16
cost 1.03–1.09 of a T = 1 pass — and the drafter's BF16 block pass at T = γ streams at 274 GB/s instead of ~110 —
which is what turned the M6 gate on this chip (dspark.md §3). On a chip without the accelerator the T > 1 GEMM
would be a `simdgroup_multiply_accumulate` kernel (Apple7+), not a wider FMA loop. Tokens per second ≈ `(1 + E[accepted]) / (t_draft + t_verify)`.
With the public drafters' reported accepted lengths (2.7–4.1 on math/code/chat at n-max 4 **[R]**) and the M5 Pro's
cost table, L = 3–4 on the shader path pays for FP8 layers but is marginal for the NVFP4 MLPs (×1.79 at T = 4), which
is exactly why the accelerator verify path (§5.6, ×1.03–1.09 up to 16 tokens) and the per-chip choice matter. On an M3 Pro
(no accelerator, T-costs unmeasured) L will be smaller. Every number here is re-measured in plan M6; the gate is
tokens/s, not acceptance.

**Correctness.** Greedy speculative decode must be token-identical to greedy non-speculative decode (the reference is our
own engine, then the HF golden); sampling verification must preserve the target distribution (rejection sampling;
distribution tests). The drafter's block is checked against the DeepSpec reference implementation on the same anchor and
context (draft tokens identical in greedy mode, confidences within 1e-3).

**The LM drafter (the second plugin, `spec/lm`).** The classical draft model — a small causal LM with the target's
tokenizer (mlx-lm's `draft_model`) — is any registered model package built with a `prefix` (its slabs, aux entries,
tables, states and activations beside the target's), run inside the round: a *first chain step* over the committed
positions the drafter has not processed plus the anchor (`StepState.n_inject + n_chain` rows from `position −
n_inject`: the prompt chunk in prefill; in decode the last draft after a full acceptance, else the anchor alone; the
argmax of the last row is the first draft), then γ − 1 single-row chain steps, each appending its k/v; the rows past
the accepted prefix are stale and are overwritten by the next chain, whose rows attend only to keys at or before
their own position. The same layer modules are lowered once per pass under a graph *activation scope*
(`Graph.scope`: sources keep their names, activations take the pass's prefix), the mixers take the pass's mode
from the lowering context (`LowerContext.mixer_attrs` → `LM_MODE`, `CHAIN_I`), and the row counts are the step
state's (`n_chain`, `n_inject + n_chain`: row sources 3 and 4). No confidences: the whole chain is verified (or a
fixed length); `drafter_ctx_len` records the chain's end, the accept scan derives the ingest rows from it. Measured
on the M5 Pro (decode-kernels.md §10): token-identical to plain decode, acceptance equal to mlx-lm's with the same
0.6B, and a chain step of 4.1 ms where mlx-lm's 0.6B step is 2.1 — the round costs more than mlx-lm's until the
small-model step is at MLX's speed per layer.

**Measured (M5 Pro, 2026-09-24; decode-kernels.md §5) [M].** The round as built: with the cost-aware rule and the
shader-FMA GEMVs, Qwen3-8B NVFP4 + its public drafter decodes at 37.5 ms per token on a plain story prompt (1.05
drafts accepted of 7) and at 27.1 ms — parity with plain decode (26.8) — on a chat-template prompt (2.14 accepted);
the draft pass costs 33 ms because BF16 at T = 7 runs ALU-bound at ~110 GB/s, and each verified draft costs the
cost table's ×1.28–×1.79, so L is capped at 3. The token-identity gate holds; the speed gate waits for the T ≥ 2
GEMM path (§5.6, M9) — the prediction two paragraphs up, now with numbers.

**Drafter provenance.** Public drafters were trained against a *particular* target quantization (Q4_K_M or NVFP4 W4A4)
by capturing that target's hidden states; our W4A16 target is close but not identical, so acceptance is measured, not
assumed. If it disappoints, the NeMo AutoModel / SpecForge / DeepSpec recipes retrain a drafter on-policy against our
dequantized reference on a GPU box (out of scope for the Apple engine; a dependency of M6). The MTP head remains a
possible second `Drafter` plugin — the contract (§5.14) is drafter-agnostic — but is not a v1 deliverable.

### 5.9 Numerics, correctness, determinism

* Reference = HF `Qwen3_5ForConditionalGeneration` on weights dequantized exactly as the pack decoder does
  (NVFP4: `LUT[q] · scale_e4m3 · scale_2`; FP8: `LUT[w] · scale`). Small same-architecture models serve end-to-end CI;
  the 27B is checked layer by layer (`--num-layers-override`) and by greedy-token match.
* Gates inherited from MPK: leaf ops vs a torch oracle (≤ 2 ULP BF16 outputs, ≤ 8 ULP FP32 state); composite layers
  cos > 0.999 with bounded max-abs; full-model greedy tokens equal to the golden except at exact logit ties; repeated
  runs bit-identical; speculative greedy decode token-identical to non-speculative greedy decode.
* Static slices (and stealing, where used) change only *who* computes a block, never the arithmetic inside it;
  reductions combine per-block partials in block order. Results are bit-deterministic.

### 5.10 Profiling and debugging

* Every op is its own dispatch, so per-op GPU timestamps come straight from counter sample buffers (one encoder per
  op in profiling builds), and Xcode GPU capture and shader validation work normally. Shader validation
  (`MTL_SHADER_VALIDATION=1`) is the test for out-of-bounds stores **[M]**: it works on the ICB replay path (the first
  violation per kernel) and per dispatch with re-encoding, and it found the three writes behind an intermittent
  wrong-token / hang / empty-generation failure of the speculative programs (the GDN commit pass storing its
  read-out through a 16-byte placeholder output, the tile's input permute of a value narrower than the slab's K, a
  drafter's context appends past its cache) that no numerical test could see until the corrupted neighbour mattered.
* For intra-op detail a **clock SIMD-group** free-runs an atomic tick counter; workers stamp block begin/end. Ticks
  are calibrated against the command buffer's `GPUStartTime/GPUEndTime`. Compile-time switch only (PR #278: a runtime
  profiling flag cost 0.4–0.5 ms/step).
* Output is `.mpktrace`; MPK's decoder and Canvas viewer are reused with tracks = (core, SIMD-group).
* Perf methodology from MPK: paired alternating A/B runs, min-of-N, never a single sample; report GB/s streamed and
  % of the chip's bound next to tok/s.

### 5.11 Extending the engine

| To add | You write | You do not touch |
|---|---|---|
| a model built from existing ops | a Python `Module` tree (`forward`, `lower`, weight-name map + transforms), a config dataclass, a registry entry, an HF golden script | kernels, runtime, compiler |
| a quantization format | a format plugin (unpack → BLM pack; MSL `decode` snippet) + oracle test | GEMV template, models |
| a new op (MoE router/experts, MLA, sliding-window attention…) | a block body in MSL + IR op (domain, class, cost) + `forward` oracle + leaf test | runtime, other ops |
| a speculative decoder | a `Drafter` module (draft ops via `lower_draft`, the select rule, the context update, its weight map) + registry entry + acceptance test | target models, kernels, runtime |
| a new chip | run the probe suite + autotuner → profile | everything else |

The rule behind the table (D16): a change that adds a model, a format, an op or a drafter lands as a new package under
the matching registry plus tests, and touches nothing else. §5.14 gives the contracts; the generality milestone and a CI
diff check enforce it.

MoE fits the static program: routing is a `REDUCE`+`SERIAL` pair writing expert ids to a buffer; expert GEMVs are `MAP`
ops whose blocks index the expert slab through those ids (PR #278's `dyn` ops) — no re-encode, no CPU. Their uneven
blocks are the natural first customer for intra-op stealing. **Built (#46):** `moe_route` (one SIMD-group per token:
softmax, top-k, the weights), `moe_gemv` (the GEMV template's *pairs mode*: the work items are (token, slot, block)
and the slab block is `ids[token][slot] · blocks_per_expert + block`, so a step streams exactly the chosen experts'
bytes; the experts of a layer are one row-stacked slab), `moe_combine` (the weighted sum, deterministic, no atomics),
and the `SparseMoE` layer module the `qwen3_moe` package uses — all as op / layer / model packages, no engine edit.

### 5.12 Inter-op overlap: what MPK V2's software pipelining becomes here

MPK V2 pipelines *across dependencies*: while op k computes or waits on its activations, loader warps stage op k+1's
weights into SMEM, so weights are never what a task waits for. Three measurements (`probes/p11_interop_overlap`, M3
Pro) say which part of that idea survives on Apple silicon:

| Measurement | Result | Meaning |
|---|---|---|
| Streaming rate vs cores used | 1 core 18.0–18.7 GB/s; 9 of 18 cores 114–126 GB/s; 12–18 cores 123–133 GB/s (up to 87 % of nominal) | the bus saturates with half to two-thirds of the cores — the rest of the ALUs idle during every bus-bound op |
| Bus-bound op ∥ bus-bound op, no barrier | 118–131 GB/s serial vs 126–131 (split cores) / 127–130 (oversubscribed): no consistent gain | **overlap cannot create bandwidth**: pre-staging op k+1's weights would only take bus time from op k — and there is no faster memory to stage them into (P8) |
| Bus-bound op ∥ ALU-bound op, no barrier, both at full crew geometry | serial 27.3 ms → overlapped 24.7 ms = the bus-bound op alone; **the ALU op fully hidden (86–114 % across runs, i.e. within noise)**, even when it is 87 % as long as its partner, in either encode order | the hardware interleaves SIMD-groups of the two dispatches on each core and fills memory-latency gaps with ALU work |
| Same pair with cores split by hand (15 ∥ 3, or 12 ∥ 6 encoded ALU-first) | 31.2 ms and 29.0 ms — *slower* than serial | placement belongs to the firmware; do not partition cores |

So V2's pipelining across dependencies does not transfer (D14), but one overlap does, and the model's dataflow offers
exactly one instance per layer: the token mixer's core is ALU/latency-bound at short context and its *gate* projection
is a bus-bound GEMV that the core does not depend on —

* GDN layer: conv → L2-norm → delta-rule recurrence needs `q, k, v, a, b`; `in_proj_z` (31 MB FP8) is consumed only by the
  final gated norm. Emit `in_proj_z` as an un-barriered sibling of the recurrence instead of row-stacking it with `qkv`.
* Attention layer: the attention core needs `q, k, v`; the output-gate half of `q_proj` (31 MB FP8) is consumed only by
  the final sigmoid gating. Same treatment. (At long context attention itself becomes bus-bound and the pair stops
  overlapping usefully.)

Expected value **[H]**: the mixer core is a few percent of a layer, so ~2–4 % of a step on the M3 Pro. It is a compiler
rule (do not stack a projection whose only consumer sits behind an ALU-bound op), costs +64 un-barriered dispatches, and
is enabled per chip by measurement.

*Built and measured (2026-09-24, #29/#35).* The layer library emits every mixer as core → gate GEMV → merge / gated
norm with the gate rows a block-aligned range of the stacked slab, and the compiler's barrier pass keeps an ICB
barrier only where an op touches what the ops before it wrote (the flag orders the flagged command behind all
preceding ones — measured, `decode-kernels.md` §3). On the 0.8B / M5 Pro the pass frees the 24 gate GEMVs and the
step drops from 6.85 to 6.58 ms per token (−3.9 %) with the core encoded first, 6.63 with the gate first — the
`sibling_order` rule holds by ~1 % within noise. The M3 Pro row is unmeasured.

**M5 Pro — measured; M4 — projected.** What matters is how over-provisioned the cores are relative to the bus. The
projection below assumed that a core streams ~18 GB/s on every chip; the M5 Pro's cores stream 29 GB/s with the M3
Pro's lane order and **71 GB/s** with the interleaved one, so the ratio moved the other way:

| Chip | GB/s per GPU core | Spare ALU during a bus-bound op |
|---|---|---|
| M3 Pro 18c (measured) | 8.5 | 33–50 % (12 of 18 cores saturate the bus) |
| M5 Pro 20c (measured, `p12` §4) | 15.4 | **70 %** — 6 of 20 cores stream 278 GB/s, 10 stream 286 |
| M3 Max 40c / M3 Ultra 80c | 10.2 | large (projected) |
| M4 10c · M4 Pro 20c · M4 Max 40c | 12.0 · 13.7 · 13.7 | unknown — Apple9 like the M3, but the M5 Pro shows the per-core rate is not a family constant; measure |
| M5 10c / M5 Max 40c / M5 Ultra 80c | 15.4 | large if their cores stream like the M5 Pro's (projected) |

The M5 Pro's overlap result (`p12` §5, three runs, the bus-bound op saturating the bus): an ALU-bound sibling is
hidden 102–126 % when it is encoded *before* the bus-bound op, up to 44 % of the partner's length, and 84–93 % at
85 % of it; encoded *after* the bus-bound op only a ≤ 22 % sibling hides (100–122 %), larger ones 1–29 %. Splitting
cores by hand was again slower than serial (21–23 vs 18 ms), and two bus-bound ops again gained nothing (292–296 →
295–297 GB/s). So the compiler rule gains a clause — *emit the ALU-bound sibling first* — that is a profile value (on
the M3 Pro order did not matter), and the expected value of the rule is higher on the M5 Pro than projected, not lower.

The same measurements settle the verification question the projection raised: a T > 1 pass on the shader ALUs turns
ALU-bound between T = 4 and T = 8 for FP8 and at T = 2 for NVFP4, which is exactly where the M5 accelerator path takes
over (§5.6, §5.8). M5 adds one opportunity with no M3/M4 counterpart, still **[H]**: inside a T > 1 GEMM, dequantizing
the next tile on the shader ALUs while the accelerator multiplies the current one (`p14` does them sequentially; MLX's
`quantized_nax` does too) — the closest Apple analogue of Blackwell's loader/mma split, relevant to verification and
prefill, not to T = 1 decode.

### 5.14 Module structure and extension contracts

The engine is organized so that a new model, format, op, drafter or chip is an *addition under a registry*, never an
edit of the engine (D16). Layout (the plan's §2 has the file-level version):

```
monolith/                Python package — front-end and compiler
  core/                  typed IR (Graph, Value, Op), dtypes, symbolic shapes (T, ctx), StepState schema, chip Profile
  nn/                    the Module contract + a layer library: Embedding, RMSNorm, QuantLinear, GQAAttention,
                         GatedDeltaNet, GatedMLP, LMHead, Sampler … each = forward() oracle + lower() + weight_map()
  models/<name>/         one package per architecture: config dataclass, module tree, HF weight-name map + transforms,
                         golden hooks; registered by HF `architectures[0]`.  The ONLY place model names appear.
  formats/<name>/        quantization plugins: unpack(checkpoint) → BLM pack, MSL decode snippet, torch oracle
  ops/                   op registry: block domain, class (MAP / REDUCE / SERIAL), cost model, kernel binding by profile
  spec/                  the Drafter contract; spec/dspark/ (block drafter, Markov + confidence heads, select rule);
                         verify/accept ops shared by all drafters
  compiler/              passes (canonicalize → fuse → select packs → partition → barriers → memory plan → emit),
                         coverage guard, program.json + MSL emission, autotune hooks
  runtime/               nanobind bindings over the C++/ObjC++ core
  monolith/backends/metal/ per-chip kernels, scheduling hooks and JSON configurations
  kernels/common/         shared Metal templates (chip overrides under kernels/<backend>/)
kernels/                 MSL block bodies + templates (common/, gemv, attention, gdn, norm, embed, sample, draft)
runtime/                 C++/ObjC++: device, packs (mmap), pipelines (function constants, binary archive),
                         ICB builder + re-encode fallback, host pump, token ring, StepState, trace
tools/                   pack_weights, bench (GEMV harness = probes/p13 grown up), goldens, viewer
tests/                   contract (no GPU) · kernels · layers · models · spec · runtime · perf · extension
```

Contracts (Python, kept minimal on purpose):

```python
class Module(Protocol):                       # every layer, every model, every drafter
    def forward(self, *xs: Tensor) -> Tensor  # torch oracle on dequantized weights — the semantics
    def lower(self, g: Graph, *xs: Value) -> Value   # emits IR ops; never touches Metal
    def weight_map(self) -> dict[str, WeightSpec]    # HF tensor name → (format, transform, pack slab)

class Model(Module):                          # models/<name>/model.py
    config: ModelConfig                       # from HF config.json
    def layers(self) -> Sequence[Module]      # the step program follows this order
    def state_spec(self) -> StateSpec         # KV / recurrent state / checkpoints the runtime must allocate
    def feature_taps(self) -> list[int]       # layers whose residual stream a drafter may read (empty if none)

class Drafter(Protocol):                      # spec/<name>/
    gamma: int
    def lower_draft(self, g, ctx: DraftContext, anchor: Value) -> DraftBlock   # tokens, confidences, hidden
    def lower_select(self, g, block: DraftBlock, profile: Profile) -> Value    # verify length L
    def lower_context_update(self, g, taps: Value, accepted: Value) -> None   # feed committed positions back
    def weight_map(self) -> dict[str, WeightSpec]

class Format(Protocol):                       # formats/<name>/
    def unpack(self, tensors: dict[str, np.ndarray]) -> DequantSpec           # exact dequant recipe (oracle)
    def pack(self, spec, layout: PackLayout) -> bytes                          # BLM pack in the profile's lane order
    msl_decode: str                                                            # snippet used by the gemv template

class OpDef:                                  # ops/registry.py
    name: str; domain: BlockDomain; klass: Literal["MAP", "REDUCE", "SERIAL"]; cost: CostModel
    kernels: dict[ProfileKey, KernelBinding]   # missing binding for the target profile ⇒ build fails (coverage guard)
```

Registries are plain dictionaries filled by decorators at import time (`@register_model("Qwen3_5ForConditionalGeneration")`,
`@register_format("nvfp4")`, `@register_op("gemv_T")`, `@register_drafter("dspark")`). The compiler consumes only
registries and the IR; the runtime consumes only `program.json`, the pack manifest and the profile. Consequences:

* *Adding a model* = `models/<name>/{config.py, model.py, weights.py}` + `tests/models/<name>/` golden script. If it
  needs a new op, that op is a separate PR under `ops/` + `kernels/` with its own oracle test. The **extension test**
  in CI fails a model PR that changes files outside `monolith/models/`, `tests/` and `docs/`.
* *Adding a drafter* = `spec/<name>/` implementing `Drafter`; the verify/accept ops, the dynamic-T program and the
  StepState fields are shared. DSpark is the first; an MTP-head or EAGLE-style drafter would be a second package.
* *Adding a format* = `formats/<name>/`; the GEMV template is parameterized by the decode snippet and the pack layout,
  and the pack ↔ checkpoint round-trip test is generic. A checkpoint written by another tool is a package matter,
  not an engine one: a package may declare two **checkpoint adapters** — a name map (`checkpoint_rename`) and a
  value map (`checkpoint_adapt`, stored values → the convention the package declares, e.g. mlx_lm folding the
  `1 +` of a zero-centered norm into the tensor) — applied by the safetensors reader for the packer and the oracle
  alike, so the engine never learns a convention.
* *A layer library, not per-model kernels.* Qwen3.8's attention layers and the DSpark drafter's attention layers are the
  same `GQAAttention` module with different configs and KV sources; the drafter's MLP is the same `GatedMLP`. Kernel
  variants are selected by (op, format, profile), never by model name.

## 7. The two questions

### 7.1 Should we use warp specialization on Apple silicon? — No.

Specialization in MPK is not an end in itself; it is how software drives *heterogeneous, asynchronous* hardware from
inside a kernel: the loader warp feeds the copy engine, the mma warp feeds tensor cores, the storer drains results
while the compute warps work, and SMEM is the software-managed buffer between them. We looked for each of those on
Apple silicon:

* **A fast scratchpad to stage into?** No — threadgroup memory costs the same as device memory **[M]**; Apple9+
  serves registers, threadgroup memory, stack and buffers from shared hardware-managed caches **[S]**.
* **An asynchronous copy or matrix engine?** No — MSL has no copy instruction; on M3/M4 `matmul2d` runs on the ordinary
  ALUs (1.05–1.21× over `simdgroup_matrix`) **[R]**; on M5 the accelerator sits inside each shader core and is invoked
  as a *collective of the calling SIMD-groups* **[S]**. This is the Hopper situation (`wgmma` is
  warpgroup-collective, so the compute warps issue it and the mma warp idles) taken to its conclusion.
* **Work to overlap?** Decode is a chain of ops that each saturate the one shared resource, the memory bus. A
  SIMD-group diverted to a side role is 1/216 of the streaming capacity lost, and a *spinning* one burns power with no
  `__nanosleep` to soften it.
* **Something to coordinate?** With one dispatch per op there is no in-kernel coordination left for a dispatcher or
  storer role to perform.

So the crew is homogeneous. What does carry over from warps is the discipline: the SIMD-group is the unit of control
flow and of cooperative kernels (32 lanes = 32 column stripes of a block), and kernels are written to its lockstep
rule. The single exception is diagnostic: the **clock SIMD-group** in profiling builds.

*What would change this:* a GPU generation exposing an asynchronously driven engine or a software-managed memory
level, or a CPU/ANE co-execution scheme that needs a GPU-side feeder. Neither exists today.

### 7.2 Should we use the static megakernel approach (PR #278)? — Static: yes. One kernel: no.

* **Static — yes.** The schedule is fixed at compile time and replayed; there is no dispatcher, instruction ring or
  task descriptor. On a single symmetric GPU running a dependency chain, a dynamic scheduler has nothing to schedule
  around: PR #278's own ledger shows V2's remaining edge was *concurrency* ("hiding producer readiness by running
  other ready tasks on stalled workers" across 148 SMs × 8 ranks with all-reduce skew) — a regime that does not exist
  here. We add what PR #278 lacked: the schedule is **compiler-generated**, which is both the generality requirement
  and the cure for its hand-maintained-invariant bugs (event-id collisions, aliased enums, out-of-range SM placements).
* **One kernel — no, for three independent measured reasons.** (1) A dispatch boundary (1.6–2.7 µs) is never
  meaningfully dearer than an in-kernel barrier (2.1–2.6 µs unfenced, 3.1–3.9 µs in the form the spec requires,
  4.7–6.1 µs with stealing), and with real work per block the difference vanishes — merging ops cannot win. (2) The
  GPU is never shared within a dispatch on Apple9 and only unreliably on Apple10, so a long kernel freezes every other
  client and invites the watchdogs. (3) Nothing is lost
  by returning: there is no fast-memory state to keep warm between ops, unlike SMEM rings and TMEM accumulators.
  PR #278 paid for its single launch with launch-lifetime rings and event math; here the firmware provides sequencing
  for free.
* **What "megakernel" means on Apple.** The unit that is compiled, fixed and GPU-resident is the *step program*, not
  a kernel: encoded once, replayed without CPU work, self-advancing, with sampling and speculative control on the GPU.
  That delivers the properties PR #278 was after — zero dispatch overhead on the host, no per-task synchronization
  lifecycle, a static whole-model schedule — through the mechanism this hardware makes cheapest.

*What would change this:* a chip/OS where dispatch boundaries are much more expensive than in-kernel barriers
(re-measured per chip by `p10`), multi-request serving with divergent per-request control flow, or multi-device
tensor parallelism over a fabric with skew — the regime where V2's dynamic scheduler earned its keep.

## 8. Risks and open questions

1. **The bandwidth result is half a microbenchmark.** BLM + crew geometry = +5 % to +17 % on raw reads on the M3 Pro; on the
   M5 Pro a real FP8 GEMV reproduced 90 % of nominal at the crew geometry but at *parity* with the conventional
   geometry, and the NVFP4 GEMV is ALU-bound at 59 % **[M]** (`p13`). M1's question is now the NVFP4 decode cost and
   the comparison against MLX `qmv` on the same machine, not the geometry. If the NVFP4 gap does not close, the decode
   win reduces to fusion + speculation.
2. **Per-load latency and decode cost.** ~40–60 ns per memory load per lane on the M3 Pro, 37 ns on the M5 Pro **[M]**,
   makes low-bit GEMV ALU/load-bound on Pro-class parts unless loads are wide and activations are reused across R rows
   × T tokens; on the M5 Pro the NVFP4 kernel is ALU-bound (the nibble decode, ~7 ops per weight), not load-bound **[M]**.
3. **Undocumented firmware behaviour.** One threadgroup per core and 12 full-speed SIMD-groups held on both chips;
   sharing granularity, the intra-block lane order that streams and the encode-order dependence of overlap all differed
   between the M3 Pro and the M5 Pro **[M]**. Design rule: *correctness depends only on documented Metal semantics* (dispatch
   ordering and ICB barriers); everything else is a per-chip profile.
4. **ICB maturity.** Compute ICBs are lightly used in production: tinygrad is the only surveyed engine that ships one,
   it needs a zero-size-dispatch workaround on M1/M2 (not on Apple9+), bind offsets are 32-bit, and two Apple-forum bug
   reports are unanswered **[R]**. Fallback: re-encode the same program each step (0.16 ms/token **[M]**, still no
   synchronization).
5. **Sharing is best-effort.** Other clients usually run between our dispatches, but one trial in six waited for a
   whole command buffer; the compositor's own behaviour was not measured. Command-buffer length is the control, and an
   on-screen frame-pacing check (plan M0) sets its default.
6. **Speculation on compute-poor chips.** T = 2–4 verification may turn base/Pro parts compute-bound (M5 Pro shader
   path: NVFP4 T = 2 already costs ×1.28, T = 4 ×1.79; the accelerator path costs ×1.5 for T = 8 **[M]**); the
   verify-length rule bounds the damage but cannot create acceptance. Gate on tokens/s, not acceptance rate.
7. **Long context.** KV traffic is 64 KB × context per step; beyond ~64 K it rivals the weights. KV quantization and a
   better long-context attention block are post-v1.
8. **Memory headroom.** 21 GB of weights + state on a 36 GB machine (28–30 GB working set) is fine; 32 GB base chips are
   tight; 24 GB does not fit — the 24 GB M5 Pro measured here reports a 19 GB working-set limit and a 14.3 GB
   `maxBufferLength` **[M]**, so it characterizes and runs kernels but never hosts the model.
9. **Reference semantics.** NVIDIA's runtime quantizes activations (W4A4/W8A8); ours does not. Token-level agreement
   with Blackwell outputs is not a goal; accuracy parity on a small eval set is.
10. **Baselines move.** MLX already has NVFP4 kernels and M5 TensorOps paths; llama.cpp follows and now drafts with
   DSpark; DFlash ships an MLX backend. Baselines are re-measured at every milestone; every claim is relative, same
   machine, same day.
11. **The drafter is someone else's.** Public DSpark drafters for the target were trained against Q4_K_M or NVFP4-W4A4
   targets, not our W4A16 semantics, and their acceptance on Apple-sized contexts is unmeasured; the BF16 one (3.7 GB)
   crowds a 36 GB machine (use the 1.3 GB NVFP4 or 2.0 GB INT8 drafter); the rank-256 Markov head costs γ vocabulary-
   wide bias GEMVs per round (~3 ms on an M5 Pro). Mitigations: measure acceptance first (llama.cpp `draft-dspark`
   on the M3 Pro), retrain on-policy with the public recipes if needed, keep the `Drafter` contract open for a second
   drafter.
