# basalt's BF16 matrix-vector kernels as nvcc compiles them

What NVIDIA's compiler emits at every rounding site of basalt's BF16-weight, fp32-activation GEMVs
(`bf16_gemv_fp32_mmvf`, `bf16_gemv_fp32_mmvf_multi`, `bf16_gemv_fp32_mmvf_cols`), read from the sm_120 PTX and SASS,
and the Metal form the port writes at each site. This page is the authority the Metal kernel follows
(`docs/design/flash-next.md`, invariant 5), as `matvec.md` is for the q8_1 quantizers and `native_mmvq`.

Basalt paths are relative to commit `b4c63b55754637f4c72ad53a0f791d425f71eb36`; `path:a-b` means lines a to b there,
and a bare `:N` is a line of the file named last.

## Method

- **Sources.** `src/kernels/cuda/native_bf16.cu` with the headers it includes (`include/basalt/kernels/`
  `bf16_gemv.hpp`, `bf16_bits.hpp`, `pdl.hpp`). Only basalt's public MIT source was sent.
- **Compilers.** Compiler Explorer's public API, as in `matvec.md`: NVCC 13.0.0 (`nvcc130`), 13.2.0 (`nvcc132`)
  and 13.3.0 (`nvcc133`), each returning the PTX and the `SASS (sm_120)` listing.
- **Flags.** Basalt's own for this file, in all three versions: `-O3 -DNDEBUG` (`CMakeLists.txt:12-14`),
  `-DBASALT_VERSION="0.0.1"` (`:7`), `--generate-code=arch=compute_120,code=[compute_120,sm_120]` (`:3-4`, `:26-31`)
  and `--use_fast_math`, which `CMakeLists.txt:185-202` sets on `native_bf16.cu`.
- **Translation unit.** `native_bf16.cu:1-137` verbatim (the includes, `mmvf_warp_sum`, both kernel templates and
  `mmvf_block_size`), the quoted local includes inlined under `#line` directives, then a table that takes the address
  of `bf16_f32_mmvf_kernel<32>`, `<64>` and `<256>` and of `bf16_f32_mmvf_multi_kernel<32, 4>`, `<256, 4>` and
  `<256, 8>`. The host launchers after line 137 hold no device arithmetic. 256 is the block every engine call on the
  decode path gets (n_in = 2560, section 3); 32 is the only block without the shared-memory stage.
- **Version check.** In every function the three versions emit the same arithmetic: the same `FFMA.FTZ` chains and
  `FADD.FTZ` butterflies in the same order. 13.0 and 13.2 emit the same instruction counts per function. 13.3 adds
  a second copy of the block-level butterfly for a diverged warp (`BRA.DIV` to `WARPSYNC.COLLECTIVE` shuffles), with
  the same adds in the same order (section 1).

## Notation

`matvec.md`'s: fl(e), fma(a, b, c), `.FTZ`, and the Metal helpers of `kernels/common/basalt_fp.metal` (`fma_ftz`,
`add_ftz`, `warp_sum_ftz`). bf(h): bf16 bits to fp32, the bits shifted left by 16, exact (`bf16_bits.hpp:45-50`).

## Summary

| Kernel | Rounding sequence nvcc 13.x emits (sm_120) | Metal |
|---|---|---|
| `bf16_f32_mmvf_kernel` (one row) | thread t: acc = fma(bf(w_lo), x.x, acc), then acc = fma(bf(w_hi), x.y, acc), per pair p = t, t + B, ... in order, from +0; all `FFMA.FTZ` | `fma_ftz` twice per pair, in the same order |
| reduction (B > 32) | XOR butterfly 16, 8, 4, 2, 1 (`FADD.FTZ`); lane 0 of warp w stores to `partials[w]` (zeroed); warp 0 runs the butterfly over all 32 `partials`, zeros included | `warp_sum_ftz`; the same zeroed threadgroup array and second `warp_sum_ftz` over 32 lanes |
| reduction (B = 32) | the warp butterfly only | `warp_sum_ftz` |
| `bf16_f32_mmvf_multi_kernel` (2 to 8 rows, NT 4 or 8) | per token k < n_tok the one-row kernel's sequence, site for site: its own accumulator, the same pair FMAs, the same two butterflies | the same kernel source with NT accumulators |

No float operation in any function lacks `.FTZ`: the PTX has 218 `fma.rn.ftz.f32` and 165 `add.ftz.f32` in each
version and no unflagged `fma`, `add`, `mul` or `sub`; the SASS no unflagged `FFMA`, `FADD` or `FMUL`. There is no
implicit contraction site: both FMAs are the source's `__fmaf_rn` (`:62-63`, `:102-103`), and nothing else
multiplies.

## 1. `bf16_f32_mmvf_kernel` (`native_bf16.cu:44-73`)

Grid n_out blocks of B threads (`mmvf_block_size`, section 3); block o computes y[o] from weight row o
(`w + o * n_in`, read as 32-bit words of two bf16 values, `:49-50`) and x (read as float2 pairs, `:51`).

| Site | basalt | PTX (13.2) | SASS (13.2) | Metal |
|---|---|---|---|---|
| `partials` zeroed (B > 32) | `:53-56` | `st.shared.b32` of 0 under `t < 32`; `bar.sync 0` | `@!P0 STS [R22], RZ`; `BAR.SYNC.DEFER_BLOCKING 0x0` | `if (t < 32) partials[k][t] = 0.0f;` barrier |
| bf16 widening | `:62-63` `f32_from_bf16((uint16_t) weight)`, `(weight >> 16)` | `shl.b32 %r22, %r19, 16`; `and.b32 %r24, %r19, -65536` | `IMAD.U32 R16, R20.reuse, 0x10000, RZ`; `LOP3.LUT R20, R20, 0xffff0000, RZ, 0xc0, !PT` | `as_type<float>(word << 16)`, `as_type<float>(word & 0xffff0000u)` |
| first FMA of a pair | `:62` `acc = __fmaf_rn(bf(lo), input.x, acc)` | `fma.rn.ftz.f32 %r23, %r22, %r20, %r145` | `FFMA.FTZ R18, R18, R16, R21` | `acc = fma_ftz(w0, in.x, acc)` |
| second FMA | `:63` `acc = __fmaf_rn(bf(hi), input.y, acc)` | `fma.rn.ftz.f32 %r25, %r24, %r21, %r23` | `FFMA.FTZ R21, R19, R20, R18` | `acc = fma_ftz(w1, in.y, acc)` |
| warp sum | `:65`, `mmvf_warp_sum` (`:37-42`) | `shfl.sync.bfly.b32 %r121\|%p11, %r145, 16, 31, -1`; `add.ftz.f32 %r122, %r145, %r121`; offsets 8, 4, 2, 1 likewise | `SHFL.BFLY PT, R2, R21, 0x10, 0x1f`; `FADD.FTZ R2, R2, R21`; ... ×5 | `warp_sum_ftz(acc)` |
| partial store | `:68` `if ((t & 31) == 0) partials[t / 32] = acc;` | `st.shared.f32` | `@!P0 STS [R2], R3`; `BAR.SYNC.DEFER_BLOCKING 0x0` | `if (lane == 0) partials[k][sg] = acc;` barrier |
| block sum | `:70` `if (t < 32) acc = mmvf_warp_sum(partials[t]);` | `ld.shared.f32`; 5 × (`shfl.sync.bfly`, `add.ftz.f32`) | `@P1 EXIT` (t > 31); `LDS R22, [R22]`; `SHFL.BFLY PT, R3, R22, 0x10, 0x1f`; `FADD.FTZ R3, R22, R3`; ... ×5 | `if (sg == 0) acc = warp_sum_ftz(partials[k][lane]);` |
| output | `:72` `if (t == 0) y[blockIdx.x] = acc;` | `st.global.f32` | `@P0 EXIT` (t ≠ 0); `STG.E desc[UR8][R2.64], R7` | `if (t == 0) y[o] = acc;` |

The same sites in the other versions, `<256>`: 13.0 `IMAD.U32 R31, R18.reuse, 0x10000, RZ`; `LOP3.LUT R18, R18,
0xffff0000, RZ, 0xc0, !PT`; `FFMA.FTZ R16, R16, R31, R19`; `FFMA.FTZ R19, R17, R18, R16`; 13.3 `IMAD.U32 R16,
R20.reuse, 0x10000, RZ`; `LOP3.LUT R20, R20, 0xffff0000, RZ, 0xc0, !PT`; `FFMA.FTZ R18, R18, R16, R21`; `FFMA.FTZ R21,
R19, R20, R18`. Some unrolled iterations widen the low half with `SHF.L.U32 R, R, 0x10, RZ` instead of the multiply
by 0x10000: the same bits.

Notes:

- **One chain per thread, in pair order.** The loop (`:58-64`) is unrolled by 8, then 4, 2 and 1 for the remainder;
  every `FFMA.FTZ` takes the previous one's result as its addend, so a thread's sum is the two FMAs of its first pair,
  then its second pair's, and so on, from +0. The front end orders each FMA's operands as the source does (weight,
  activation, accumulator); `ptxas` swaps the two factors (`FFMA.FTZ R18, R18, R16, R21`: the activation `R18` times
  the weight `R16`). The product of two floats is commutative and exact inside the fused operation, so the bits do not
  change.
- **The butterfly's operand order.** The source adds the received value to its own (`value + shfl`), as the PTX
  does; the SASS adds them the other way. Float addition is commutative (a NaN's payload aside), so the Metal form
  keeps the source's order. Every lane ends with the same bits: both lanes of a butterfly pair add the same two
  values.
- **The block sum adds zeros.** With B = 256 the warp partials p0..p7 sit in `partials[0..7]` and `partials[8..31]`
  stay +0. Warp 0's butterfly over the 32 slots adds +0 to every partial in its 16 and 8 steps, then gives
  ((p0 + p4) + (p2 + p6)) + ((p1 + p5) + (p3 + p7)). An add of +0 can change only a zero's sign (−0 + +0 is +0), which
  the port reproduces by running the same 32-lane tree over the same zeros.
- **Flush to zero.** `--use_fast_math` implies `-ftz=true`: each `__fmaf_rn` becomes `fma.rn.ftz.f32` and each `+=`
  `add.ftz.f32`, so a subnormal bf16 weight (exponent field 0), a subnormal activation, a subnormal running sum and a
  subnormal result all become the zero of their sign. `fma_ftz` and `add_ftz` flush explicitly, so the Metal kernel
  does not depend on what the GPU does with subnormals (this one flushes them in arithmetic anyway: `matvec.md`,
  Notation).
- **13.3's diverged-warp copy.** 13.3 guards the block sum with `BRA.DIV UR4`: a warp that is not converged runs a
  second copy of the five steps through `WARPSYNC.COLLECTIVE` / `SHFL.BFLY` / `ENDCOLLECTIVE`, with the same
  `FADD.FTZ` sequence (`FADD.FTZ R3, R22, R3`, then `R2, R3, R2`, `R5, R2, R5`, `R4, R5, R4`, `R7, R4, R7`). Warp 0 is
  converged there (it reaches the line together after the barrier), so the copy never runs; it changes no bit either
  way. It accounts for 13.3's extra counts: `<256>` has 14 `FADD.FTZ` and 15 `SHFL.BFLY` against 10 and 10 in 13.0 and
  13.2.

## 2. `bf16_f32_mmvf_multi_kernel` (`native_bf16.cu:78-122`)

The same grid and block, for n_tok (1..8) activation rows x + k·ldx and outputs y[k·ldy + o], NT = 4 or 8 accumulator
slots (section 3). `partials[NT][32]` is zeroed under `t < 32` (`:86-91`); per pair the weight word is widened once
(`:97`), then per token `k < n_tok` (`:99-105`) the one-row kernel's two FMAs on that token's accumulator
(`:102-103`); then per token the warp butterfly, the lane-0 store to `partials[k][t / 32]`, the block butterfly over
`partials[k][t]` and, from thread 0, the store of each `k < n_tok` (`:107-121`).

| Site | SASS (13.2, `<256, 4>`) |
|---|---|
| zeroing | `@!P0 STS [R2], RZ`; `@!P0 STS [R2+0x80], RZ`; `@!P0 STS [R2+0x100], RZ`; `@!P0 STS [R2+0x180], RZ`; `BAR.SYNC.DEFER_BLOCKING 0x0` |
| widening, once per pair | `IMAD.U32 R30, R12.reuse, 0x10000, RZ`; `LOP3.LUT R37, R12, 0xffff0000, RZ, 0xc0, !PT` |
| token k's pair, under `k < n_tok` | `@P1 FFMA.FTZ R24, R30, R24, R9`; `@P1 FFMA.FTZ R9, R37, R25, R24` (token 0; tokens 1..3 likewise under `@P3`, `@P4`, `@P2`) |
| warp sums | 4 × (`SHFL.BFLY` + `FADD.FTZ`) × 5, the tokens' steps interleaved, each token's offsets 16, 8, 4, 2, 1 in order |
| partial stores | `@!P0 STS [R4], R9`; `[R4+0x80]`; `[R4+0x100]`; `[R4+0x180]`; `BAR.SYNC.DEFER_BLOCKING 0x0` |
| block sums | `LDS R3, [R2]`; `LDS R6, [R2+0x80]`; ...; 4 × 5 butterfly steps, interleaved |
| outputs | `@P3 STG.E desc[UR4][R4.64], R7`, then one `STG.E` per further token under `n_tok > k` |

**Result: per token the multi kernel computes the one-row kernel's sequence, site for site, in the three versions.**
Each token's FFMA chain is the one-row chain on that token's activations (the pair order, the operands, the flush),
predicated on `k < n_tok`; the compiler interleaves the tokens' independent chains and butterflies but never mixes
two tokens' values. Slots k ≥ n_tok keep +0 and are never stored. So each output is bit-identical to a
`bf16_f32_mmvf_kernel` launch on its own row, as the kernel's comment says (`:75-77`), and `<32, 4>` (no shared
stage: 40 `FFMA.FTZ`, 20 `FADD.FTZ`, 20 `SHFL.BFLY`, 4 `STG.E` in every version) is the B = 32 one-row kernel per
token.

Instruction counts per function (13.0 = 13.2; 13.3 adds the diverged-warp copy of section 1 to each block sum):

| Function | `FFMA.FTZ` | `FADD.FTZ` 13.0 / 13.3 | `SHFL.BFLY` 13.0 / 13.3 | `STS` | `LDS` 13.0 / 13.3 |
|---|---|---|---|---|---|
| `bf16_f32_mmvf_kernel<32>` | 30 | 5 / 5 | 5 / 5 | 0 | 0 / 0 |
| `bf16_f32_mmvf_kernel<64>`, `<256>` | 30 | 10 / 14 | 10 / 15 | 2 | 1 / 1 |
| `bf16_f32_mmvf_multi_kernel<32, 4>` | 40 | 20 / 20 | 20 / 20 | 0 | 0 / 0 |
| `bf16_f32_mmvf_multi_kernel<256, 4>` | 40 | 40 / 59 | 40 / 60 | 8 | 4 / 7 |
| `bf16_f32_mmvf_multi_kernel<256, 8>` | 48 | 80 / 119 | 80 / 120 | 16 | 8 / 15 |

The `FFMA.FTZ` counts are the unrolled loop bodies (15 pairs in the one-row kernel; 20 pair FMAs over 4 tokens per
multi iteration, plus the remainder loop), not a per-output count.

## 3. Launches (`native_bf16.cu:124-203`)

Host code, no arithmetic, but it fixes the block size B and so the summation order:

- `mmvf_block_size(n_in)` (`:124-135`): start at 32 with ceil(n_in / 64) iterations; each candidate 64, 96, ..., 256
  replaces the best only with strictly fewer iterations, ceil(n_in / (2 · candidate)). n_in = 2560, every engine call
  on this path, gives 256 (5 pairs per thread); n_in ≤ 64 gives 32.
- `bf16_gemv_fp32_mmvf` (`:162-189`): n_in positive, even and at most INT_MAX, n_out positive and at most INT_MAX,
  x 8-byte aligned, w and y 4-byte aligned; grid n_out, block B.
- `bf16_gemv_fp32_mmvf_multi` (`:139-160`): `n_tok == 1 && ldy >= n_out` calls the one-row kernel (`:141`);
  otherwise n_tok in 1..8, even n_in and ldx, x 8-byte aligned (`:142-144`), and the multi kernel with NT = 4 for
  n_tok ≤ 4, else 8 (`:146-150`).
- `bf16_gemv_fp32_mmvf_cols` (`:193-203`): ncols contiguous columns (ldx = n_in, ldy = n_out) in chunks of 8; a chunk
  of one takes the one-row kernel, the others the multi kernel.

## 4. Metal

`kernels/common/basalt_mmvf.metal` is one source for both kernels: the macro `BLOCK` is B and `NT` the accumulator
slots (1 for the one-row kernel, 4 or 8 for the multi kernel); `monolith/kernels.py` (`basalt_mmvf_macros`,
`basalt_mmvf_params`, `basalt_mmvf_cols`) reproduces section 3. A thread's index is t = 32 · sg + lane, so its pairs,
its warp and its `partials` slot are basalt's whatever order Metal gives the SIMD-groups. Each site is the form in
the tables above: `fma_ftz` twice per pair, `warp_sum_ftz` for both butterflies, the zeroed `partials[NT][32]` in
threadgroup memory, the block stage only for BLOCK > 32. `tests/kernels/test_basalt_mmvf.py` checks the kernel bit
for bit against a numpy emulation of this page (`tests/kernels/basalt_emu.py`) and every multi-row and column output
bitwise against the one-row kernel.
