Workload: Apple M6 (Apple11, 12 GPU cores), 32 GiB unified memory, Qwen3.8-27B-NVFP4 + DSpark, seven proposals, fixed verification, temperature zero, 128 output tokens. Each prompt is context minus 128 tokens. The first output token comes from prefill; decode throughput measures the remaining 127 tokens. No prefix hit is included in timings. Model loading, compilation, short warmups and shader validation are excluded. The same synthetic reference-notes prompt is used within each context.

## PV and merge

The previous approximately 188 ms merge number was cumulative across 16 target and five draft attention layers in one 128-token chunk at position 32384: target 185.906 ms plus draft 2.489 ms. It was not a single layer. Probability partials moved PV multiplication from the score kernel to the second stage; therefore 185.9 → 504.2 ms compares different amounts of work. The second-stage increase alone does not establish a merge regression.

A diagnostic split writes full FP32 PV partials, merges partitions, performs inverse rotation/normalization/rounding, then gates. It reproduces output bytes but deliberately adds large intermediate memory traffic and launches. The split times below are **not an additive decomposition of the fused production kernel**. Packed V decoding remains fused into tile loading; its standalone GPU time is unavailable.

| bf16 | 50.482 | 62.683 | 22.045 | 10.517 | 0.015 | 0.019 |
| q8_0 (QM8 diagnostic) | 140.294 | 152.118 | 28.699 | 10.537 | 0.015 | 0.020 |

The Q8 fused experimental QM=8 chain takes about 140 ms even though separately warmed score and PV stages sum to about 94 ms. Cache state and encoder boundaries differ; summing isolated runs or subtracting them from ICB time is invalid. The device exposes only timestamp counters, supports stage boundaries but not dispatch-boundary sampling, and has 32768 bytes maximum threadgroup memory. `xctrace` is unavailable in the installed developer tools. Actual DRAM transactions, occupancy, GPU frequency and stall attribution were not measured.

The selected tile is 16 query/head rows and eight SIMD groups; the score tile and KN reduction length stay unchanged. Quantized V read demand at T=128 falls from 96 to 48 loads per cached row. At 32K attended keys, including the new query rows, this is Q8 3264 → 1632 MiB and Turbo4 1584 → 792 MiB per target layer. The historical 32640-row portion accounts for Q8 3251.250 → 1625.625 MiB and Turbo4 1577.813 → 788.906 MiB. These are packed-row footprints multiplied by load calls, not measured DRAM transactions or counts of redundant scalar metadata loads. BF16 already uses a 16-row PV tile. Static PV threadgroup memory rises from 18560 to 20736 bytes for quantized KV. No additional device intermediate buffer or full historical BF16 cache is allocated.

At attended 32K/T128 there are 512 64-key partitions per query. The original FP32 partial payload is 1536 MiB per target layer; probability payload is 192 MiB, plus 12 MiB of max/denominator metadata in either scheme. Existing fallback buffers remain allocated. Ordered partition correction, denominator FMA, BF16 probability rounding, final inverse rotation, normalization, output rounding, permutation and gate ordering are preserved.

32-row PV tiles and four-SIMD-group variants were rejected after complete-chain screening. Turbo4 16-row tiling regresses small query counts: at 32K, T16 is about 11.89 → 12.19 ms and T32 about 23.72 → 23.84 ms. T64 improves about 47.22 → 45.39 ms. The optional policy keeps the original tile below 64 active rows, including the 64K/T32 workload. BF16 retains its existing tile. Q4, mixed KV, draft, verification, other shapes and other chips keep their existing fallbacks.

Original fused score/PV MMA is retained as a measured control and fallback. Naively widening its quantized query tile to 16 would require 40960 bytes of threadgroup query/KV/probability/score storage, exceeding the device limit; further refusion needs deliberate scratch-lifetime reuse and new validation. The standalone split was rejected because its extra FP32 writes/reads make the full chain slower.

## Decision and remaining limits

The implementation is available behind the M6 profile option `engine.attention_pv_tiling`, which remains **absent/disabled in the production profile**. It requires the existing probability-partial route. Enabled explicitly, it selects 16-row/eight-SIMD PV for symmetric Q8 and for Turbo4 with at least 64 active query tokens; Turbo4 shorter rows and BF16 retain their existing PV layout. Decode/verification are unchanged.

No whole-model current/candidate pair at 8K–32K was swap-free on both sides. Raw Q8 prefill reductions are about 5.0%, 6.7% and 8.1%; raw Turbo4 reductions are about 0.7%, 1.1% and 1.8%. Under the requested rule these observations cannot qualify a production default. The current default implementation is therefore retained. The 64K/T32 policy has no changed kernel to promote.

No verified code-path decode regression was found, so no speculative dispatch rollback was applied. In the strict 8K BF16 sequence the old version moves from 14.360 to 14.125 tok/s and current from 14.356 to 14.097 tok/s: both share about 1.6–1.8% run-order drift. Their adjacent paired differences and fixed-state differences are much smaller. This supports treating unpaired historical comparisons as confounded, without establishing a unique thermal, frequency, residency or swap cause.

Remaining work: obtain repeated full-model no-swap pairs before enabling the optional policy; extend the measured 32K row-count crossover sweep to shorter contexts; investigate the still-dominant QK/FP32 PV work with hardware counters; assess compact fallback workspace so 64K can use larger prefill chunks within the memory budget; and evaluate scratch-lifetime reuse for further score/PV fusion while preserving partition and rounding order. Gate/inverse epilogues are too small in the measured split to explain the large second-stage cost.
